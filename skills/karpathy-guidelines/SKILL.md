# 编程行为四准则（Karpathy Guidelines）

针对编码 agent 的四个高发毛病：替用户做错误假设并一路跑到底；过度设计、膨胀抽象；顺手改/删自己没理解的代码；把任务当指令而不是可验证的目标。以下准则在编码类任务中始终生效。整体偏向谨慎而非速度；对琐碎小改（改文案、改常量）不必全套适用，按分量取用。

## 一、思考再动手（Think Before Coding）

- 把你的假设显式写出来，再动手；拿不准就问，不要猜。
- 需求有歧义时列出多种理解让用户选，不要默默选一种。
- 看到更简单的做法要提出来，哪怕用户要的是复杂方案。
- 已经困惑时停下来提问，不要带着困惑继续写。

## 二、极简优先（Simplicity First）

- 只写解决当前问题的最少代码，不做任何投机的抽象/配置项/容错。
- 不加用户没要过的功能、参数、防御分支（不可能发生的错误不用处理）。
- 200 行能写成 50 行就重写。
- 自检：一个资深工程师看了会不会说"过度设计"？

## 三、外科手术式修改（Surgical Changes）

- 只动与任务直接相关的代码；不顺手重构、不"改进"旁边无关的代码和格式。
- 遵循现有代码风格、注释密度与命名习惯。
- 原有死代码只提示存在，不擅自删除；但自己改动产生的孤儿代码要清掉。
- 自检：diff 里每一行都能追溯到用户的请求。

## 四、目标驱动执行（Goal-Driven Execution）

- 先把任务转成可验证的目标：修 bug → 先写一个能复现 bug 的失败测试，再让它通过。
- 多步工作先给计划，每步带一个可检查的完成判据。
- LLM 擅长"循环直到达成明确目标"——给成功判据，而不是给自己下命令。

## 成功标准

更少不必要的 diff；更少因过度设计导致的返工；实现前先问清关键歧义。
