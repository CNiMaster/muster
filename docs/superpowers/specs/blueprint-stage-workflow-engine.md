# 蓝图工作流引擎：stages 从图纸变调度（批次④）

状态：M1 已实施（2026-08-29；M2 阶段门自检/M3 画布运行视图待拍板）
前置：批次①②③已交付——预制蓝图带默认 stages、画布/AI 编辑可写回 stages（版本化）、共享契约 `src/shared/blueprint-stages.ts`。本批回答「画上的线怎么真的跑起来」。

## 0. 调研锚点（2026-08-29 实施前调查：知名工作流产品怎么做）

| 范式 | 代表 | 核心机制 | 本批取舍 |
|---|---|---|---|
| 线性管道 | Zapier | 触发器→线性动作，分支=拆多条流 | 取其「简单事简单做」：线性 stages 是默认形态 |
| 节点 DAG | n8n / Dify / GH Actions / Airflow | 节点=能力调用，边=控制流；**节点级状态可见+节点级重试/从失败步重跑** | 取节点级状态（StageRun 行）+ 失败停在当前阶段重跑（游标不动） |
| 持久执行 | Temporal | 事件溯源+确定性重放，状态可恢复可暂停 | 取「状态持久化+断点续跑」：stage 行冻结蓝图快照，任务中断后重领从当前阶段继续 |
| 状态图+检查点 | LangGraph | 显式图拥有控制流，agent 拥有语义；checkpointer 支持人审中断 | 取「引擎拥有控制流」——阶段推进由引擎拦截判定，不是 agent 对话自发；waiting_input 即天然人审中断点 |
| SOP 装配线 | MetaGPT（PM→架构→工程→QA 各角出结构化产物） | 角色×阶段，阶段间交接**结构化产物**而非聊天记录 | 取产物交接：每阶段 summary+artifacts 落 stage 行并注入下一阶段上下文；worktree 跨阶段延续 |

关键否定项：不做可视化 BPMN（结构只有 BlueprintStage）；不让 agent 自报阶段跳转（LangGraph 教训：显式控制流>自主闲聊）；不每阶段开新任务（保持单任务贯穿，任务树不膨胀，worktree/验收/终链语义不变）。

## 0.5 v1 执行模型（单任务贯穿 + 引擎拦截推进）

- **建阶段行**：任务领取时若穿了带 stages 的蓝图（inputProtocol.blueprintMatched）且非机制任务（讨论/建议/蜂群蜂/外包承接豁免）→ 从蓝图 stages **冻结快照**建 `task_stage_run` 行（跑动中蓝图被改/回滚不影响本任务）。
- **上下文注入**：systemPrompt 追加「阶段工作流」段——全链路概览、当前阶段 k/N（label/description/参与人）、**前序阶段产出摘要**（MetaGPT 式交接）、只做本阶段的指令。
- **完成拦截**：run 以 completed 收口时，若还有未完成阶段：当前阶段标 passed（summary/artifacts 落行）→ 下一阶段标 running → 任务**不 completed**，经专用迁移 running→queued 放回队列（task_event: stage_advanced）；**阶段改派**——下一阶段 staffingPersonaIds[0] 解析（项目专家池常驻专家 > 保留现任），改写 assignee；worktree 保留（跨阶段产物/工作现场连续）。末阶段完成才走原 completeTask（验收/终链/反思/进化记账全部照旧）。
- **失败/等待**：失败重试、waiting_input、审批暂停、H8 停止全部原样——stage 游标不动，恢复后重跑**当前阶段**（n8n 式 retry-from-failed-step）。
- **观测**：每阶段推进在现场对话播报里程碑（「✅ 阶段 k/N 完成…→ 进入 k+1（XX 上岗）」，对齐「执行过程即对话现场」口径）+ realtime task.stage_advanced + `GET /api/tasks/:taskId/stages` + 任务详情阶段进度卡。

## 1. 为什么立项（问题陈述）

蓝图目前的用户观感是「专家团」：任务穿上蓝图后，实际执行的还是 负责人 + 蜂群 那一套（`task-engine/engine.ts`），蓝图的 stages 字段不被任何执行路径消费。连线画布、AI 阶段提案于是都成了「图纸」——看得到，跑不动。

用户的三个灵魂拷问（2026-08-29 拍板时原话精神）：

1. **用户能否知道要做什么？** 任务开始后，用户看不到「这套打法分几步、现在走到哪步」。
2. **连线的目的是什么？** 如果线只是装饰，画布就是负担。
3. **什么是工作流？** 需要一个产品级定义，而不是工程私语。

### 工作流的产品定义（本 spec 的锚）

> 工作流 = 这类活分几步走、每步谁上、每步交出什么、下一步接什么。
> 蓝图把「专家团」升级成「流水线」：阶段是节拍器，不是摆设。

## 2. 目标 / 非目标

**目标**

- 任务穿上带 stages 的蓝图后，按阶段推进：上一阶段产出是下一阶段输入。
- 用户在任务现场随时看到「当前阶段 k/n · 阶段名」，能看懂、能干预。
- 阶段级战绩回写蓝图（哪一步常返工），让进化有更细的颗粒度。

**非目标（明确不做）**

- 不做通用 BPMN/可视化编排引擎——阶段数据结构只有已定的 `BlueprintStage`（id/step/label/description/dependsOn/staffingPersonaIds），够用为止。
- 不动「用户只对负责人说话」的中央六岗制；阶段不是新的对话入口。
- 不替换蜂群派遣；阶段是任务内的推进节拍，派遣仍是每阶段内「谁上」的实现方式之一。
- 不做阶段级人工审批流（审批已有 semanticHighRiskReview 体系，不复用不混淆）。

## 3. 执行模型（草案）

### 3.1 阶段会话（StageRun）

- 任务创建时若穿戴蓝图且有 stages → 初始化阶段游标 `stageCursor = 0`；无 stages → 行为与现状完全一致（**零蓝图/零阶段任务不受影响**，这是兼容底线）。
- 每个阶段一个 StageRun：绑定阶段的 `staffingPersonaIds`（缺省=主槽人设），产出物先进任务级 staging 区（沿用 `muster/<pid>/pt-<ptid>` 集成区语义）。
- 阶段完成判定：阶段产出通过当前门的检查（见 3.2）→ 游标推进到 dependsOn 满足的下一个阶段（并行分叉允许同时多个就绪阶段，但 v1 建议串行化执行、只允许多入边单活跃，简化心智）。
- 全部阶段完成 → 走现有终态/验收/复盘链路（engine 现有 completed 路径不动）。

### 3.2 阶段门（Stage Gate，2026-08-29 用户定调：可选、工作流自有，非全局强制验收）

- 门是**工作流定义的一部分**，不是平台强制：stage 声明 `gate`（缺省 `none`）——
  - `none`（默认）：run 以 completed 结束即过（M1 现状，绝大多数阶段用这个）；
  - `self-check`：轻量自检——对照阶段 description 核对本阶段产出清单，不过停在当前阶段重跑，不惊动用户；
  - `acceptance`：验收员人设快评 pass/fail——留给「这步错了后面全白干」的关键阶段（如终稿前审校），由蓝图作者/AI 提案按任务需要标注。
- 是否需要门、需要哪种门，取决于这类活的实际需要（蓝图说了算），不是每阶段强制验收。
- fail → 停在当前阶段重跑（复用任务级自动重试/失败卡三动作），不产生新 Task；连续 fail 达上限 → 现有 waiting_input/blocked 语义上抛。

### 3.3 记账升级

- `evolveBlueprintById` 现按任务记胜负；升级为附阶段维度：`stageStats[stageId] = { runs, rework }` 存 blueprint 行（或 sidecar 表，倾向新表 `blueprint_stage_stat` 防行膨胀）。
- AI 优化对话的 digest 带上「哪一步返工最多」，让「调整阶段」提案有数据依据（批次③的意图驱动闭环补上弹药）。

## 4. UX 直觉要求（验收即答三问）

1. **知道要做什么**：任务现场（对话流顶部或工作块）常驻「阶段进度条 k/n + 阶段名 + 一句阶段说明」；点开看每阶段谁上、交什么。
2. **连线有目的**：画布是**协作关系图**——工作流（阶段及其先后）、人员（谁参与哪个阶段）、工具（哪个阶段用哪些家伙）都在画布上，线条表明协作关系并持久化为语义连接（人员→阶段=staffingPersonaIds 引擎真改派依据；工具→阶段=阶段技能亲和）。**不做运行过程可视化**（2026-08-29 用户定调：运作过程太复杂，不必展示给用户；自动优化的依据在内部做，不露复杂度）。
3. **工作流是什么**：蓝图详情的工作流卡（批次①已加）+ 新建任务穿戴蓝图时的创建卡预览一句话：「将按 N 步流水线推进：A → B → C」。

## 5. 数据与 API 草案

- 新表 `project_task_stage_run`：`id, project_task_id, blueprint_id, stage_id, status(pending/running/passed/failed), attempt, started_at, finished_at, artifact_ref`。
- Task 侧加 `stage_cursor`（或从 stage_run 推导，倾向推导少一源）。
- API：`GET /api/tasks/:taskId/stages`（M1 已实施，任务级；载体级聚合视图后续按需）、阶段失败上抛复用现有失败卡端点。
- 契约复用 `src/shared/blueprint-stages.ts`，不新造字段。

## 6. 风险与开放问题

- **阶段粒度失控**：AI 提案可能拆出过细阶段（8 个上限可能还不够唠叨）——靠 describeStages 摘要与 UX 预览控制心智负担。
- **与 breadthTier 的关系**：档位封顶总量，阶段切分粒度——两者正交还是联动（细阶段 × 高档位 = 昂贵）待定。
- **staging 产物交接**：阶段间产物引用机制（路径 vs 元数据）需要和 staging 看门狗对齐。
- **并行分叉 v1 是否砍掉**：dependsOn 已支持 DAG，但执行侧 v1 串行化更稳，只保留数据结构表达力。
- **回滚语义**：任务跑到阶段 3 时用户回滚蓝图 stages——进行中的任务按快照继续（StageRun 建 run 时冻结蓝图 stages 快照），新任务用新版。

## 7. 里程碑（2026-08-29 用户复盘后重塑）

- **M1（已实施 2026-08-29）**：串行阶段推进——task_stage_run 表+task-stage 域模块+引擎三处挂接（领取建行/上下文注入/完成拦截改派回队）+现场播报+stages API+任务详情阶段卡。无 stages 蓝图与机制任务零行为变化（fail-open：阶段机制任何异常回落旧收口路径）。
  - **M1 灵活性边界（用户问询定调）**：阶段内的灵活协作不受管线约束——执行者中途需要帮手（如「让人物塑造专家设计个新角色再回传」）走既有蜂群派遣/咨询/桥接分派，在 run 内发生、结果回传继续本阶段；阶段等外部依赖（waiting_dependency）恢复后仍是同一阶段。管线接管的只有「阶段结束时『下一个给谁』」——控制流归引擎（LangGraph 教训），语义与临时协作归 agent。
  - **一蓝图多工作流：暂不做（定案）**。组织 = f(活)：同活不同打法应裂成不同蓝图，匹配层天然路由；阶段分叉已可由 dependsOn 表达。等真实使用撞到「同一张蓝图确实要两套流程」再议（先走蓝图裂变承接）。
- M2（待拍板，重塑后）：**可选阶段门**（stage.gate 声明式：none 默认/self-check/acceptance，见 §3.2——门是工作流的事，不是强制验收）+ **阶段级记账**（哪一步常返工，被动观测无强制；喂 AI 优化对话做内部自动优化依据，保持简单不过度）+ 可选：**阶段级技能亲和**（阶段绑 skill → 按阶段做能力预检，对齐自动化的 requires 语义；注意与「任务显式 requiredSkillIds 时不穿蓝图」的既有规则打通）。
- M3（待拍板，重塑后）：**画布协作语义连接**——人员↔阶段、工具↔阶段的连线从「纯排布 sidecar」升格为持久化语义（人员→阶段已由 staffingPersonaIds 承载并被引擎消费；补工具→阶段亲和），画布成为这张打法的协作关系总图。**明确不做运行过程可视化。**

每步都保持「无 stages 蓝图 = 现状行为」的兼容底线，可随时停在任何里程碑。
