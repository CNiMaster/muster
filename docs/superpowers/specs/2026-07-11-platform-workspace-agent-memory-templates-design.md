# Muster 平台工作区、员工记忆、执行器、权限与模板设计

> 日期：2026-07-11
>
> 状态：已完成用户确认，待实施计划
>
> 适用版本：Muster vNext
>
> 关联文档：[Muster Agent 公司工作台 PRD](../../PRD-agent-company-workbench.md)

## 1. 背景与目标

Muster 不是小说写作工具，也不是绑定某一个模型或 CLI 的编程工具。它是一个本地单用户、多公司、多项目、持久员工制的 Agent 公司工作台。长篇小说只是第一个完成纵向闭环的公司模板。

vNext 的目标是同时解决两类问题：

1. 平台能力已经很多，但首次使用和日常页面暴露了过多内部概念，用户难以判断下一步。
2. 员工身份、执行器、记忆、项目目录、权限和模板尚未形成统一、可扩展、可分享的产品层。

设计原则是“复杂能力，简单入口”：普通用户通过向导、自然语言 Task 和待处理中心完成工作；员工线程、镜像、工作流图、执行器、会话压缩、Token 与发布记录仍然完整保留，但按需展开。

## 2. 已确认的产品边界

- 本地单用户优先；“公司”是软件内的组织概念，不代表真实企业租户。
- 总工作区内一个目录对应一个项目；一个公司可以拥有多个项目。
- 每个 Task 在项目的独立 Git worktree 沙盒中执行，再通过发布队列合并回项目正式目录。
- 员工绑定固定执行器。公司可以提供统一默认执行器，员工可以固定覆盖。
- 员工之间以员工身份通过 Task 协作；Codex 指挥 Claude Code 的真实语义是“绑定 Codex 的员工给绑定 Claude Code 的员工派发 Task”。
- 同一执行器可以被多个员工使用，但每次运行必须隔离。
- 本地员工支持仅能力复制、完整快照复制和引用同一个员工。
- 对外分享只能包含能力，不得包含记忆、凭据、会话、项目数据和本地路径。

## 3. 信息架构

全局导航只保留四项：

1. **工作台**：最近项目、需要用户处理、正在工作和最近完成。
2. **公司**：公司模板、部门、员工、组织、通信、工作流和运行状态。
3. **员工库**：员工个人空间、本地复用、能力包导入与分享。
4. **设置**：工作区、执行器、凭据引用、权限策略和高级运行配置。

Task、成果、用量、复盘、人物关系、线程和镜像属于项目内部页面，不进入全局导航。

### 3.1 首次启动

固定流程如下：

`选择总工作区 → 选择公司类型 → 组建团队 → 配置执行能力 → 新建项目 → 发布第一个 Task`

#### 选择总工作区

- 默认建议 `~/MusterWorkspace`，允许用户选择其他路径。
- 检查目录是否可写、Git 是否可用、已有 CLI 和 API 配置。
- 检测细节默认隐藏，只在需要用户处理时展示。

#### 创建公司

- 选择公司模板：长篇小说、软件开发、研究与报告、内容与媒体、数据分析、自定义或导入。
- 公司模板生成部门、推荐员工、通信关系、工作流、成果协议和权限默认值。

#### 组建团队

- 默认展示模板推荐团队，允许增减岗位。
- 员工可以新建、从员工库招募、引用同一个本地员工或复制能力/快照。
- 执行器默认继承公司设置；员工级固定覆盖位于高级设置。

#### 新建项目

- 默认创建在 `{workspace}/{company}/projects/{project}`。
- 用户只需填写项目名称和目标，目录可以修改但不要求手写绝对路径。

#### 发布第一个 Task

- 用户输入自然语言目标。
- Muster 展示负责人、推荐参与员工、工作范围和权限摘要。
- 用户确认后进入项目工作台。

### 3.2 日常启动

- 默认返回上次打开的项目。
- 显示退出期间完成、失败、安全暂停和等待审批的 Task。
- 首页优先展示“需要你处理”“正在工作”“最近完成”。
- 新建公司、项目、员工和模板导入仍然可从全局入口主动发起。

### 3.3 渐进展示

默认展示目标、Task、成果和团队动态。以下内容折叠在“管理与高级功能”中：

- 员工线程和镜像
- 组织、通信与工作流图
- 执行器状态和原始日志
- Token、费用和上下文大小
- 会话压缩与轮换
- 沙盒、发布和回滚记录
- 权限规则

## 4. 工作区、项目与 Task 沙盒

推荐目录结构：

```text
MusterWorkspace/
├── .muster/
│   ├── agents/
│   ├── runtimes/
│   ├── state/
│   └── runtime/
└── companies/
    └── {company}/
        └── projects/
            └── {project}/
```

- 项目目录是用户可见的正式工作目录和 Git 仓库。
- Agent Home、执行器 session、记忆索引和凭据引用保存在 `.muster/`，不得污染项目仓库。
- 每个 Task 创建独立 worktree。员工、镜像和 API 文件工具只能写入该 Task worktree。
- 发布队列负责测试、冲突检查、三方合并、发布记录和回滚。
- 访问项目外路径必须经过权限中心；只读参考项目不等于写入授权。

## 5. 员工、任职与执行器

### 5.1 领域分层

```text
AgentProfile（全局员工档案）
  ↓ 招募、引用或复制
CompanyEmployee（公司任职实例）
  ↓ 分配到项目
ProjectAgentThread（项目线程）
  ↓ 领取 Task
ExecutionRun（一次执行）
```

#### AgentProfile

- 稳定身份、人格、原则、通用能力、Skills 和个人长期记忆。
- 可以在本地跨公司引用，也可以复制为独立快照。

#### CompanyEmployee

- 公司岗位、部门、职责、通信权限、公司记忆、固定执行器绑定和权限策略。
- 同一个 AgentProfile 在不同公司的任职上下文相互隔离。

#### ProjectAgentThread

- 项目上下文、Task 历史、压缩摘要、项目记忆和执行器 session。
- 同一员工进入不同项目时线程和上下文相互隔离。

#### ExecutionRun

- 由 `companyId + employeeId + projectId + threadId + taskId + runId` 唯一标识。
- 保存工作目录、进程、日志、中止信号、用量和结果。

### 5.2 固定执行器

- 公司配置一个默认执行器。
- 员工可以继承默认值或固定覆盖为 Codex CLI、Claude Code CLI、Gemini CLI、OpenAI 兼容 API、Gemini API 或自定义 CLI。
- 运行期间不自动更换员工执行器。执行器不可用时 Task 进入阻塞，用户修复或修改绑定后重试。
- 员工身份、记忆和 Task 归属不依赖某个执行器 session。

### 5.3 同一执行器的多员工隔离

可以共享：

- CLI 程序、版本、登录凭据引用、默认模型和不可变配置。

必须隔离：

- Agent Home、项目线程、session、worktree、进程、日志、临时目录、中止信号和 Task 状态。

同一员工同一项目的主线程默认串行；不同员工可以在独立 worktree 并行。同一员工需要并行时创建镜像线程。

执行器适配器必须声明并检测并发能力。无法隔离全局可写状态的 CLI 使用执行器配置级串行锁，并在 UI 明确显示限制。

## 6. 通用执行器平台

### 6.1 Adapter Manifest

每种 CLI 通过版本化 Manifest 描述：

- 官方来源和支持平台
- 检测命令和最低版本
- 安装、升级、回滚和卸载方式
- prompt、模型、cwd 和结构化输出参数
- session 创建、恢复、压缩和中止方式
- 独立配置目录和临时目录能力
- 权限与 Turbo 参数映射
- 流式事件、用量和错误解析
- 并发隔离能力

首批官方适配器：Codex CLI、Claude Code CLI、Gemini CLI、OpenAI 兼容 API、Gemini API和自定义 CLI。

### 6.2 自动安装

`检测现有版本 → 展示官方来源/版本/安装位置 → 用户确认 → 下载或调用包管理器 → 校验 → 登录/凭据配置 → 连接与沙盒能力测试`

- 不允许公司模板静默安装任意程序。
- Muster 管理版本安装在 `.muster/runtimes/{executor}/{version}`。
- 系统版本只记录路径和版本，不由 Muster 自动升级。
- 凭据只引用系统钥匙串、环境变量、CLI 登录状态或本地加密存储。

### 6.3 API 工作目录

API 没有操作系统 cwd。Muster 通过 `read_file`、`write_file`、`edit_file` 等受控工具代理 Task worktree，使 API 与 CLI 共享相同的沙盒、权限、成果检查和发布流程。

## 7. 权限与 Turbo

权限由两个正交配置组成：

`审批策略 × 允许范围`

### 审批策略

- 每次询问
- 按规则询问
- 无需审批
- 完全禁止

### 允许范围

- 当前 Task 沙盒
- 当前项目
- 总工作区
- 指定目录
- 整台设备

Turbo 等于“无需审批 × 用户选择的范围”，不是独立权限系统。范围外仍然询问或拒绝。

审批操作支持：拒绝、单次允许、始终允许此命令、始终允许此目录和输入自定义规则。自定义规则可以限制命令、参数、目录、文件类型、员工、公司、项目、网络、子进程和有效期限。

删除项目外文件、系统软件安装、凭据访问、Git push、部署、外部消息、账号操作和付费行为作为单独高风险类别；普通 Turbo 不自动放开。

## 8. 员工个人空间与分层记忆

### 8.1 Agent Home

```text
agents/{agentId}/
├── profile/
│   ├── SOUL.md
│   ├── principles.md
│   ├── capabilities.yaml
│   └── skills/
├── memory/
│   ├── CORE.md
│   ├── USER.md
│   ├── daily/
│   ├── lessons/
│   └── index/
├── companies/{companyId}/
├── projects/{projectId}/
├── sessions/{projectThreadId}/
└── scratch/
```

数据库保存权威索引、权限、来源和状态；Markdown/YAML 为可读、可编辑、可迁移的上下文载体。

### 8.2 记忆层级

1. **身份**：人格、原则和固化能力，始终加载。
2. **个人核心记忆**：稳定用户偏好和通用经验，精炼后加载。
3. **公司任职记忆**：只在当前公司加载。
4. **项目记忆**：当前项目按需加载。
5. **历史记录**：消息、Task 和工具日志只在搜索时读取。
6. **执行器会话**：仅是缓存，可以丢失和重建。

### 8.3 每次执行的上下文顺序

1. 员工身份与原则
2. 当前公司岗位和章程
3. 当前项目目标与关键决定
4. 项目线程压缩摘要
5. 检索到的相关记忆和最近 Task
6. 当前 Task 工作包
7. 可联系员工、工作流分支、权限与工具

### 8.4 借鉴 OpenClaw 与 Hermes Agent

采用以下已验证模式：

- 每个 Agent 拥有独立 workspace、状态和 session store。
- 长期精炼记忆与详细近期日志分开。
- 压缩前强制执行 memory flush，防止关键上下文随压缩丢失。
- 稳定身份文件与项目上下文文件分离。
- 活跃记忆使用小型冻结快照，完整历史按需全文/语义搜索。
- Skills 作为程序性记忆渐进加载。
- 记忆和 Skill 写入支持审批、版本和差异。
- 所有上下文文件和外部能力包经过提示注入与凭据窃取扫描。

OpenClaw workspace 默认只是 cwd 而非强沙盒；Muster 不采用这一弱边界，继续使用 Task worktree 和发布队列。

参考资料：

- https://docs.openclaw.ai/concepts/multi-agent
- https://github.com/openclaw/openclaw/blob/main/docs/concepts/memory.md
- https://github.com/openclaw/openclaw/blob/main/docs/concepts/agent-workspace.md
- https://hermes-agent.nousresearch.com/docs/user-guide/features/memory
- https://hermes-agent.nousresearch.com/docs/user-guide/features/personality
- https://hermes-agent.nousresearch.com/docs/user-guide/features/context-files
- https://hermes-agent.nousresearch.com/docs/user-guide/features/skills

### 8.5 记忆写入流水线

`Task/对话结束 → 提取候选 → 去重和注入扫描 → 判断个人/公司/项目/Skill 范围 → 自动写入或等待审批 → 建立来源和版本 → 更新索引`

每条记忆记录内容、范围、来源 Task/消息、创建者、可信度、用户确认状态、生效条件、过期时间和是否允许影响未来操作。

默认模式为“重要记忆审批”：项目事实可以自动写入；个人长期记忆和 Skill 提升进入待确认区。

### 8.6 压缩与恢复

触发条件包括 Token 阈值、Task 数量、会话时长、执行器轮换和用户手动整理。

`暂停领取 → memory flush → 保存决定/承诺/依赖/阻塞 → 生成线程摘要 → 保留旧 session → 创建新 session → 注入重建上下文 → 继续执行`

压缩失败不得删除旧 session 或旧摘要。用户可以查看、纠正、锁定、删除记忆，也可以开启新会话、清理项目记忆、恢复基础能力和创建员工快照。

## 9. 员工复用与分享

### 本地复用

1. **仅能力复制**：复制身份、能力、Skills、推荐执行器和权限模板，不复制记忆。
2. **完整快照复制**：按用户选择复制个人记忆和经验；复制后各自成长。
3. **引用同一个员工**：共享身份、能力和个人通用记忆；公司、项目、Task、session 和 worktree 仍隔离。

### 对外分享

对外上传的是员工能力包，只能包含身份简介、工作原则、岗位能力、Skills、工具需求、推荐执行器类型、推荐权限、成果协议和版本信息。

禁止上传个人/公司/项目记忆、消息、Task、凭据、session、本地路径和成果内容。

## 10. 专业角色与提示词资产治理

### 10.1 现状

仓库当前跟踪：

- 212 个 `personas/` 文件，主要来自 `agency-agents-zh`。
- 22 个 `skills/` 文件，主要来自 `addyosmani/agent-skills`。
- 5 个 `agents/` 基础文件。

这些资产目前没有接入 `src/` 运行链路。它们应被视为候选原料，而不是已经可用的员工能力系统。

### 10.2 能力包结构

外部长提示词必须被拆成版本化结构：

- 稳定身份与沟通风格
- 职责和禁止越界事项
- 专业能力标签
- Skills 与工具依赖
- Task 输入/输出协议
- 成果类型和验收标准
- 失败模式与升级路径
- 推荐执行器能力和权限范围
- 来源、许可证和版本

不把“虚构从业年限”“夸张成功指标”和大段通用知识直接注入每次 prompt。

### 10.3 导入与评测流水线

`获取来源 → 许可证/版本记录 → 静态安全扫描 → 结构化转换 → 重复/冲突检查 → 场景测试 → 人工批准 → 发布能力包`

场景测试至少验证：职责边界、输出契约、工具选择、信息不足时追问、拒绝越权、与其他岗位协作、提示注入抵抗和 Token 成本。

### 10.4 可参考来源

- 当前内置 `personas/` 与 `skills/`。
- Agent Skills 开放规范与示例：https://github.com/agentskills
- Agency Agents：https://github.com/msitarzewski/agency-agents
- VoltAgent 专业开发子 Agent：https://github.com/VoltAgent/awesome-claude-code-subagents

外部仓库只能作为导入源；能力包进入 Muster 前必须固定版本、保留许可证和通过本地评测。

## 11. Task 发布与员工协作

### 11.1 默认发布

用户只输入自然语言目标并可添加参考资料。Muster 自动推荐负责人、参与员工、工作流、成果和权限摘要；高级选项才显示优先级、截止时间、依赖、指定员工、验收标准、预算和派发深度。

### 11.2 员工间协作

- 正式工作通过子 Task 派发，保留负责人、沙盒、成果、用量和来源链。
- 信息不足时原 Task 进入等待补充，在同一 Task 对话中追问，回答后恢复。
- 只有需要独立负责人、成果或验收时才创建子 Task。
- AI-AI 对话默认显示人类可读摘要，原始消息和工具日志按需展开。

### 11.3 用户介入

用户可以补充、暂停、取消、更换负责人、修改验收标准、拒绝成果、要求重做和处理审批。普通暂停先请求安全检查点，紧急停止才终止进程并保留沙盒。

### 11.4 防循环

平台检测无变化回派、重复 Task、同一失败循环重试、无新信息追问、超过派发深度和成本/工具异常。触发后进入负责人或用户待处理，不继续自动消耗。

## 12. 公司模板平台

模板包含：元数据、创建向导、部门、岗位、员工能力包、组织/通信图、工作流、Task 协议、成果定义、权限默认值、执行器要求、触发器、复盘、健康检查和示例项目。

模板有版本和成熟度：开箱可用、需要配置、实验性、仅组织蓝图。更新模板必须显示差异，不覆盖公司本地修改。

模板不得携带记忆、凭据、session 和本地路径。用户可以用模板员工，也可以从个人员工库替换岗位。

### 12.1 首批正式模板

1. 长篇小说公司：迁移现有实现为正式模板 v1。
2. 软件开发公司：第二个重点纵向模板。
3. 研究与报告公司。
4. 内容与媒体公司。
5. 数据分析公司。

游戏开发、产品设计、办公文档和电商运营在多模态、连接器或外部审批能力成熟后进入正式支持。

### 12.2 软件开发公司 v1

#### 默认部门

- 产品与项目
- 技术研发
- 质量保障
- 运营监察

#### 必需员工

- 项目负责人
- 产品经理
- 架构师
- 软件工程师
- 测试工程师
- Code Reviewer
- 运营监察

可选员工包括前端、后端、移动端、数据库、DevOps、安全、设计和技术文档工程师。

#### 标准工作流

- 新功能：需求澄清 → 代码库分析 → 技术方案 → 用户确认 → 并行开发 → 测试 → Review → 修复 → 发布。
- Bug：复现 → 根因 → 回归测试 → 修复 → 定向验证 → 影响检查 → Review → 合并。
- 审查：读取真实 diff → 风险分级 → 验证问题 → 审查意见 → 用户决定是否修复。

#### 默认权限

- Task worktree 和项目读取默认允许。
- 项目写入只通过 worktree 与发布队列。
- 工作区其他项目读取、安装依赖、Git push 和部署需要审批。
- 凭据读取默认禁止，Turbo 默认关闭。

## 14. 分阶段改造顺序

### 阶段 0：修复新手流程

- 统一首次向导。
- 修复自动上班后无法创建项目。
- 隐藏原始 CLI/JSON 错误。
- 增加动态下一步卡片。
- 第二次打开恢复上次项目。
- 设置与高级配置分层。
- 修复长路径和错误文本横向溢出。

### 阶段 1：总工作区和项目工作台

- Workspace 实体和目录管理。
- 项目切换、最近项目和用户待处理中心。

## 15. 验收原则

- 首次用户可以不理解线程、镜像、执行器细节而完成公司、团队、项目和第一个 Task。
- 第二次启动能恢复上次项目、待处理事项和员工上下文。
- 原执行器 session 丢失后，员工能从 Muster 记忆重建并继续回复。
- 两名员工使用同一执行器时不会共享 session、cwd、日志或 Task 沙盒。
- API 和 CLI 使用相同的项目边界、审批和发布流程。
- 重要记忆可审查、纠正、删除和追溯来源。
- 模板和能力包不含凭据、记忆、session、本地路径和项目数据。
- 现有小说模板、Task、worktree 和发布队列行为保持可用。
- 每个阶段必须通过类型检查、单元/集成测试、生产构建、关键 E2E 和差异检查。

## 16. 非目标

- 本轮不实现多租户 SaaS、支付、真实企业人事系统或强租户安全边界。
- 不把员工执行器改成可在运行中自动切换的路由器。
- 不允许模板或能力包静默安装软件、获取凭据或扩大权限。
- 不把全部历史对话和日志注入每次模型上下文。
- 不在本设计阶段直接实现功能；实施范围由后续改造计划拆解。
