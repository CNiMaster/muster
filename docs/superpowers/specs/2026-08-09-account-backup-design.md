# 账号网络备份架构设计（后续项目，未实现）

> 日期：2026-08-09
> 状态：设计稿（本次仅落地本地导出/导入 MVP，本文件是网络同步的后续规划）
> 关联：`src/server/domain/backup-export.ts`（本地备份格式，本设计的上层复用）

## 背景与目标

Muster 定位为「打包 Mac 原生程序、本地运行」。用户已确认备份原则：

- **备份结构化数据**：公司/部门/员工、人才档案（含用户修改过的预置人）、技能（名称与安装来源）、插件与 MCP 配置（不含密钥明文）、权限模板、执行器配置。
- **不备份公司文件**：工作目录、素材/产物文件、git worktree 不进备份包——体积大、可能涉及隐私；提供目录指引由用户自行备份文件系统。
- **本地版已可导出/导入**（`/api/backup/export`、`/api/backup/import`，JSON 单文件）。

本设计回答：**账号登录后，如何把这份备份安全地上传到服务器、跨设备恢复、按账号配额管理**。

## 备份什么 / 不备份什么（边界）

| 类别 | 内容 | 进备份包 | 说明 |
|---|---|---|---|
| 公司 | 名称/类型/charter/contractJson/归档状态 | ✅ | 结构化 |
| 部门 | 名称/规则 | ✅ | 结构化 |
| 员工 | 档案（soul/原则/能力/推荐执行器）+ 任职（角色/职责） | ✅ | 含用户改过的预置人 |
| 人才档案 | 全部 agent_profile（含 temp 标志） | ✅ | 用户修改内容随包 |
| 技能 | tool_registry 中用户自定义项（名称/安装来源/检查命令） | ✅ | builtin 工具随程序分发，不备份 |
| 插件/MCP | manifest（command/url/args）+ 凭据**键名引用** | ✅ | 不读密钥值 |
| 权限模板 | permission_policy | ✅ | 结构化 |
| 执行器 | executor_profile 配置（binaryPath/模型名） | ✅ | 不含登录态 |
| 公司文件 | worktrees / MusterWorkspace / agents 目录 | ❌ | 体积 + 隐私；目录指引让用户自行备份 |
| 密钥 | 明文 API Key / 登录 token | ❌ | 只备份环境变量名/引用 |
| 运行时 | task 中间状态 / 运行日志 / 会话 | ❌ | 不具恢复价值 |

## 账号维度与同步模型

```
┌──────────────┐   本地导出（已有）   ┌──────────────┐   HTTPS + 加密   ┌──────────────┐
│  本地 Muster  │ ──────────────────▶ │  备份中心 UI  │ ──────────────▶ │  云备份服务   │
│  muster.db    │ ◀────────────────── │  （设置页）    │ ◀────────────── │  每账号配额   │
└──────────────┘    导入/恢复        └──────────────┘    下载 + 校验   └──────────────┘
```

- **账号维度**：备份以用户账号为粒度，一个账号一份「备份集」（快照版本序列）。
- **多设备**：最后写入胜出 + 版本号（`backupVersion` 单调递增）。设备 A 导出 v5，设备 B 导出 v6 → 以 v6 为准；恢复前比对设备本地版本，提示「本地有更新，覆盖会丢失」。
- **冲突策略**：不自动合并（结构化数据合并语义复杂）；提供「本地版本 vs 云端版本」时间线选择。

## 加密与隐私

- **传输**：HTTPS（TLS 1.2+）。
- **静态存储**：备份包用「用户密码派生的密钥」加密（PBKDF2/scrypt → AES-256-GCM），**服务器只存密文**，无法读取公司/人员内容。密钥不上传。
- **密钥引用**：MCP 的 envKeys 只存键名；即使包被解密，也没有明文凭据。
- **可选匿名化**：导出前可选择「脱敏人才姓名/公司名」（替换为 hash 前缀），用于不想暴露真实信息的场景。

## 服务器空间估算与配额

| 数据量 | 估算 |
|---|---|
| 单公司备份（结构化 JSON） | ~50-200 KB（不含文件） |
| 100 家公司 + 500 档案 | ~5-30 MB（gzip 后） |
| 每账号配额 | 建议 50 MB（宽松）；超限提示归档旧版本 |

策略：
- 备份按版本序列保存（保留最近 N=5 个版本，旧版本自动清理）。
- 公司文件不进包，配额压力极小；未来若开放文件备份，单独按「存储桶」计费。

## API 契约（草案）

```
POST   /api/account/backups                # 上传备份集（multipart，JSON + 加密）
GET    /api/account/backups                # 列出版本序列（id/版本号/时间/大小）
GET    /api/account/backups/:id/download   # 下载（校验 + 解密在本地进行）
DELETE /api/account/backups/:id            # 删除某版本
GET    /api/account/backups/:id/diff       # 与本地备份的差异摘要（恢复前确认）
```

认证：沿用账号体系的 JWT（登录态）；无账号的本地模式不调用这些端点。

## 与本地备份的关系

- 本地导出格式（`muster-backup` v1）就是云备份包的「明文形态」；云上传时对同一 JSON 做加密封装。
- 恢复流程统一：无论本地导入还是云端下载，都走 `importMusterBackup` 同一入口。
- 目录指引（`/api/backup/directories`）在云端恢复时同样返回，提示用户恢复后自行还原公司文件目录。

## 实现分期建议

1. **P1（本地，已完成）**：导出/导入 JSON + 目录指引 + 系统扫描导入 skill/MCP。
2. **P2（账号基础）**：账号注册/登录体系（本地 App 内的账号页），JWT。
3. **P3（云备份）**：备份上传/下载/版本管理端点 + 配额 + 加密封装。
4. **P4（多设备）**：版本冲突提示、时间线选择、自动备份开关（本地变更后静默上传）。

## 开放问题

- 账号体系是否需要独立服务器 + 存储（成本），还是先接第三方对象存储（S3/OSS）？
- 是否支持「公司级分享」（把某公司备份分享给他人）？涉及权限边界，暂不设计。
- 加密密码遗忘的恢复路径（无密码不可解密——需在账号页明示「忘记密码 = 丢失云端备份」的风险）。
