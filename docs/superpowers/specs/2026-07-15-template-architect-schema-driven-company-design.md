# Muster 模板架构师与声明式公司蓝图设计

> 日期：2026-07-15
> 状态：待用户书面确认
> 适用范围：公司创建、公司模板、业务知识模型、员工能力绑定、运行健康指引

## 1. 背景

Muster 是通用多 Agent 公司工作台，不是小说创作器。小说公司只是第一个纵向模板。当前实现已经能从内置模板创建部门、员工、组织关系、通信关系、工作流和首个项目，但模板类型、成果类型、页面文案和智能生成器仍包含明显的小说硬编码。

后续用户应当只描述“我要成立什么公司、解决什么问题”，由一个系统级“公司模板架构师 Skill”生成完整、可编辑、可验证的公司蓝图草案。平台使用统一的 HTML 模块化确认页展示草案；用户按推荐方案创建后，仍可独立修改部门、岗位、业务字段、视图、流程、触发器、能力绑定和健康规则。

## 2. 设计目标

1. 用户通过自然语言生成可运行的公司草案，而不是手工理解所有底层配置。
2. 平台层不认识“人物、伏笔、API、客户”等行业词，只认识声明式记录、字段、关系、事件、视图、责任、过程和规则。
3. 公司模板定义行业术语、字段结构、默认视图、负责人、协作者、维护协议、工作流、自动过程和健康检查。
4. 每个业务字段可以有独立负责人、协作人员、能力要求、输入输出和更新规则。
5. 公司模板架构师 Skill 只负责生成或修订草案，不参与公司日常业务执行。
6. 员工业务 Skill 由特定员工在特定 Task 中按需加载；字段本身不执行 Skill。
7. 草案以统一、简洁、可比较的 HTML 页面呈现，默认突出推荐方案和少量必要决策。
8. 所有生成结果必须经过结构校验和健康检查，问题必须给出人话说明、影响和修复入口。
9. 现有小说公司和成果保持可用，并迁移为通用模板引擎上的正式模板 v1。

## 3. 非目标

1. 不允许模板生成器输出并执行任意 JavaScript、Shell 或服务端代码。
2. 不在创建公司时自动生成、安装或审核新的外部 Skill。
3. 不要求普通用户查看 JSON、数据库字段、执行器参数或完整工作流内部结构。
4. 不在第一阶段实现模板市场、云端共享、多租户发布或自动安装第三方程序。
5. 不让 AI 直接覆盖已经投入使用的公司配置或用户本地修改。

## 4. 方案比较与结论

### 方案 A：为每种公司开发专用页面和领域代码

优点是单一行业体验可高度定制；缺点是每增加一种公司都要修改数据库枚举、服务端分支和前端页面，最终把 Muster 变成多个互不兼容的垂直应用集合。该方案不采用。

### 方案 B：让 AI 直接生成 HTML、配置和运行逻辑

优点是表面灵活；缺点是页面不统一、配置不可验证、存在脚本注入和权限扩大风险，也无法稳定升级。该方案不采用。

### 方案 C：声明式模板包 + 通用引擎 + 模板架构师 Skill

平台提供稳定的模板契约、通用视图、流程、健康检查和运行时能力解析；模板架构师 Skill 只生成符合契约的数据草案；React 根据草案渲染受控 HTML。该方案兼顾自动化、统一体验、安全和行业扩展，作为正式方案。

## 5. 核心概念

### 5.1 公司模板包

`CompanyTemplatePackage` 是可版本化的完整公司能力包，至少包含：

- 元数据与适用场景。
- 创建向导需要的问题和默认值。
- 部门、岗位和员工建议。
- 组织关系、通信关系和升级关系。
- Task 输入输出协议。
- 业务知识模型。
- 通用视图配置。
- 工作流、事件触发器和定时触发器。
- 员工能力要求和推荐 Skill 绑定。
- 权限与执行器要求。
- 健康规则、故障指引和示例项目。

模板中的所有对象使用稳定 `key`；用户可以修改显示名称而不破坏引用。

### 5.2 业务知识模型

平台提供以下通用原语：

- `recordType`：一种业务记录，例如小说模板中的人物、软件模板中的 API。
- `fieldDefinition`：记录字段，定义类型、是否必填、显示方式和维护协议。
- `relationType`：记录之间的关系，例如人物关系或模块依赖。
- `eventType`：带时间、参与者和来源的业务事件。
- `artifactType`：文件或长文本成果类型。
- `viewDefinition`：列表、卡片、看板、关系图、时间线、矩阵、文档或指标视图。
- `changePolicy`：直接修改、负责人审核或第一负责人审核。

字段的“专属能力”不是一个新 Skill，而是 `FieldMaintenanceContract`：

- `ownerRoleKey`：主要负责人。
- `collaboratorRoleKeys`：允许协作或提供输入的岗位。
- `requiredCapabilityIds`：维护该字段所需的业务能力。
- `recommendedSkillIds`：执行相关 Task 时推荐加载的现有 Skill。
- `inputRequirements`：开始工作前必须获得的信息。
- `outputRequirements`：必须提交的结构和证据。
- `updatePolicy`：手动、事件触发、定时或按需更新。
- `reviewPolicy`：谁可以使变更成为正式事实。
- `validationRules`：完整性、一致性和引用约束。
- `failureGuideId`：失败时展示的处理指引。

### 5.3 两类 Skill

1. **公司模板架构师 Skill**：系统级能力，只在创建、重新生成或修订公司蓝图时运行。
2. **员工业务 Skill**：绑定员工能力，在具体 Task 需要时由上下文装配器按需加载。

字段不直接调用 Skill。字段触发维护 Task，Task 指定负责人和所需能力，负责人运行 Task 时才加载对应 Skill。

## 6. 公司模板架构师 Skill

### 6.1 输入

- 公司名称和业务目标。
- 行业、主要交付物和目标客户。
- 用户指定的必须岗位、限制或偏好。
- 可用执行器、权限策略和已安装 Skill 清单。
- 可选基础模板及其版本。

普通用户只需提供公司名称和目标；其余信息由架构师生成合理默认值，并把真正无法推断的内容标为少量待确认项。

### 6.2 输出

架构师必须输出符合 JSON Schema 的 `CompanyTemplateDraft`，不得输出任意 HTML 或代码。草案包括：

- 公司说明和推荐理由。
- 部门、岗位、负责人和协作关系。
- 业务记录、字段、关系、事件和成果类型。
- 每个字段的维护协议和责任映射。
- 默认视图及展示名称。
- 工作流、Task 协议、触发器和复盘规则。
- 岗位能力要求与现有 Skill 推荐绑定。
- 权限和执行器能力要求。
- 健康规则、风险、缺口和处理指引。
- 首个项目和首个项目任务建议。

### 6.3 生成流水线

```text
用户描述
  → 选择基础模板或空白模板
  → 公司模板架构师 Skill 生成结构化草案
  → Schema 校验与稳定 key 规范化
  → 引用、责任、通信、能力和权限健康检查
  → 必要时执行一次受限结构修复
  → 平台渲染 HTML 蓝图确认页
  → 用户按推荐方案创建或进入模块编辑
  → 再次校验
  → 保存模板快照并创建公司
```

模型不可用、超时或输出连续两次无效时，平台加载最接近的内置模板草案并显示“智能方案暂时不可用，已载入可编辑推荐方案”，不得制造成功假象。

## 7. HTML 公司蓝图确认页

### 7.1 安全渲染

HTML 必须由 React 使用受控组件根据结构化草案生成。禁止渲染模型输出的原始 HTML，禁止 `dangerouslySetInnerHTML`，禁止模板携带脚本、远程样式或动态组件代码。

### 7.2 信息结构

确认页固定使用以下模块：

1. **公司概览**：目标、主要交付物、推荐方案摘要。
2. **团队与责任**：部门、员工、第一负责人和主要对接关系。
3. **业务信息中心**：记录类型、关键字段、默认视图和字段负责人。
4. **工作如何流转**：主要 Task 路径、自动触发和人工审核点。
5. **能力与运行条件**：员工 Skill、执行器和权限要求。
6. **风险与建议**：阻断问题、普通提醒和创建后优化建议。

默认视图只展开摘要和必须决定的项目；字段详情、完整关系、协议和技术配置放在“高级设置”中。

### 7.3 视觉预设

平台内置三种受控密度预设，共用设计令牌和组件：

- `guided`：默认，面向首次用户，解释较多、一次只突出一个主要行动。
- `compact`：适合熟悉系统的用户，信息密度更高。
- `visual`：强调组织、流程和视图预览，不增加新的配置项。

系统根据草案复杂度默认选择 `guided` 或 `compact`，用户可以切换，但不要求在创建前选择风格。

### 7.4 操作语义

- 主按钮：`按推荐方案创建`。
- 次按钮：`调整配置`。
- 低频操作：`重新生成`、`保存为模板草案`。
- 固定提示：`建议先按推荐方案创建；员工、字段、视图和流程创建后仍可随时调整。`

重新生成必须展示差异，不得静默覆盖用户已经修改的模块。

## 8. 能力绑定与运行时加载

### 8.1 绑定层级

- **岗位级**：岗位长期需要的能力和默认 Skill。
- **员工级**：员工最终继承或覆盖后的 Skill 清单。
- **字段级**：维护字段时需要的能力、推荐 Skill 和责任协议。
- **任务级**：本次 Task 实际要求加载的 Skill，是运行时最小集合。

### 8.2 解析规则

1. 模板架构师只能从已安装、已启用且权限兼容的 Skill 清单中推荐绑定。
2. 推荐 Skill 必须显示“由谁使用、用于什么工作、何时加载”。
3. 创建公司时，可信内置 Skill 可以按推荐方案绑定员工；用户之后可以删除或替换。
4. 未找到匹配 Skill 时保留能力要求并显示缺口，不生成、不安装新 Skill。
5. Task 创建时根据字段维护协议、工作流节点和显式要求计算 `requiredSkillIds`。
6. 上下文装配器只加载本次 Task 的 Skill 内容，不向所有员工注入全部 Skill。
7. Skill 加载失败时 Task 进入可解释的等待或阻塞状态，并给出替换、移除要求或调整任务的操作。

## 9. 变更、版本和独立配置

1. 公司创建时保存所用模板版本和完整模板快照。
2. 公司后续修改以本地覆盖层保存，不反向修改内置模板。
3. 部门、岗位、字段、视图、触发器和健康规则均可独立启用、停用或修改。
4. 模板升级只生成差异提案，区分上游新增、上游修改、本地修改和冲突。
5. 删除仍被字段、流程或 Task 引用的员工、Skill 或视图时必须先显示影响范围。
6. 模板稳定 key 不因中文名称修改而变化。
7. 已创建公司的项目数据、员工记忆、session、凭据和本地路径不进入模板导出。

## 10. 健康检查与故障指引

### 10.1 创建前静态检查

- 缺少第一负责人。
- 稳定 key 重复或引用不存在。
- 字段没有负责人或负责人岗位不存在。
- 必填字段没有任何产出或维护过程。
- 工作流断裂、无终点或形成不受控循环。
- 员工需要的 Skill、执行器能力或权限不可用。
- 通信关系不允许实际工作流所需的派发或上报。
- 视图引用不存在的记录、字段或关系类型。
- 触发器没有目标岗位或输出目标。

### 10.2 运行期检查

- 字段长期未维护或负责人离线。
- 自动触发连续失败。
- Skill 无法加载或已被禁用。
- 业务记录相互冲突。
- 字段变更长时间无人审核。
- 工作流节点持续拥堵或循环回派。
- 模板更新与本地覆盖发生冲突。

### 10.3 指引卡片

每个问题统一展示：

- `发生了什么`
- `会影响什么`
- `可能原因`
- `推荐处理`
- `立即修复` 或 `前往设置`
- `稍后提醒`（仅非阻断问题）

健康检查只提出确定性修复或生成可预览的修复草案，不擅自改变公司方向、员工权限或正式业务数据。

## 11. 通用知识与成果中心

平台提供统一的“知识与成果中心”，模板负责命名和配置：

- 列表视图。
- 卡片视图。
- 看板视图。
- 关系图。
- 时间线。
- 矩阵。
- 文档视图。
- 指标总览。

小说模板可以配置人物卡、人物关系图和故事时间线；软件模板可以配置需求列表、模块依赖图和发布路线图。新增公司类型不应要求新增专用 React 页面。

Markdown 继续作为长文本、正文、说明和导出格式；结构化记录、关系、事件、负责人、版本和来源由 SQLite 管理。派生视图只读取权威数据，不作为第二份可编辑事实。

## 12. 数据与接口边界

实施阶段应引入以下独立领域边界，具体表结构在实施计划中锁定：

- `template_definition`：模板身份、来源和当前版本。
- `template_version`：不可变模板清单和校验结果。
- `company_template_installation`：公司采用的版本、快照和本地覆盖。
- `knowledge_type_definition`：记录、字段、关系、事件和成果类型。
- `knowledge_record`：项目或公司的结构化业务记录。
- `knowledge_relation`：记录关系。
- `knowledge_event`：业务事件与叙事/计划时间。
- `knowledge_change`：Agent 或用户提交的变更提案、审核状态和来源。
- `capability_binding`：岗位、员工、字段和 Task 的能力/Skill 绑定。
- `health_finding`：健康问题、影响、指引和处理状态。

通用领域接口不得接受小说专用枚举。所有外部生成结果先通过共享 Zod Schema，再进入领域层。

## 13. 兼容与迁移

1. 把现有 `general`、`software`、`content`、`novel` 转换为内置模板包 v1，保留原稳定 id。
2. 保留现有公司 `kind` 读取兼容，但新代码从模板安装快照读取能力。
3. 把 `character_sheet`、`worldbuilding`、`timeline`、`foreshadowing` 等类型迁入小说模板注册表；已有 Artifact 路径和 kind 保持可读。
4. 将专用人物关系页迁移为通用关系图视图配置，旧路由可以重定向。
5. 将当前只列出 Skill 名称的上下文行为保留为兼容回退；新版 Task 优先使用版本化 Skill 引用。
6. 将当前硬编码为小说的 Setup Assistant 改为调用模板架构师 Skill 和通用草案 Schema。
7. 迁移必须幂等，不删除现有公司、项目、成果、Task 或员工绑定。

## 14. 子项目拆分与顺序

该设计包含多个可独立验收的子系统，必须按以下顺序实施，每个阶段保持产品可运行：

### 阶段 1：声明式模板契约与注册表

- 建立共享模板 Schema、模板版本存储、注册表和健康校验。
- 把四个现有模板迁入注册表。
- 公司创建继续可用，行为不倒退。

### 阶段 2：模板架构师 Skill 与通用草案生成

- 新增系统级模板架构师 Skill。
- 生成通用 `CompanyTemplateDraft`。
- 支持验证、一次修复、离线回退和草案保存。

### 阶段 3：模块化 HTML 蓝图确认页

- 用通用组件渲染草案。
- 实现推荐创建、模块编辑、差异重新生成和视觉密度预设。
- 不暴露原始 JSON。

### 阶段 4：业务知识模型与通用视图

- 建立记录、字段、关系、事件、变更提案和通用视图。
- 将小说成果和人物关系迁到模板配置。
- 用软件模板验证无小说硬编码。

### 阶段 5：员工 Skill 按需解析与 Task 输出协议

- 建立岗位、员工、字段和 Task 四层能力绑定。
- 上下文按 Task 加载 Skill。
- Task 支持结构化知识变更、关系、事件、问题和后续任务输出。

### 阶段 6：健康中心、修复指引和模板升级

- 持久化健康发现。
- 提供创建前和运行期指引。
- 实现模板版本差异、本地覆盖保护和修复草案。

## 15. 测试策略

1. **Schema 单测**：合法模板、非法引用、重复 key、缺少负责人、无效视图和不兼容 Skill。
2. **生成器单测**：有效生成、无效输出修复、模型失败回退、禁止额外字段和禁止代码载荷。
3. **领域集成测试**：模板版本、公司快照、本地覆盖、升级差异和幂等迁移。
4. **运行集成测试**：字段触发 Task、负责人解析、Task Skill 最小加载、知识变更审核和健康发现。
5. **UI 单测**：六个蓝图模块、默认折叠、推荐创建、模块修改、风险卡片和视觉预设。
6. **E2E**：自然语言生成公司 → 查看 HTML 草案 → 按推荐创建 → 修改字段负责人 → 运行首个 Task。
7. **兼容回归**：现有小说公司创建、小说成果初始化、章节维护触发器、人物关系视图和现有四模板流程保持通过。
8. **安全测试**：原始 HTML、脚本字段、超大嵌套、无权限 Skill、危险路径和模板凭据均被拒绝。

## 16. 验收标准

1. 用户用一句自然语言可以获得结构完整且可运行的公司蓝图草案。
2. 草案以统一 HTML 模块显示，普通用户无需理解 JSON、枚举或执行器内部结构。
3. 用户可以直接按推荐方案创建，并明确知道所有配置之后仍可修改。
4. 每个关键字段都能追溯到负责人、协作者、维护协议、所需能力和故障指引。
5. 页面能明确说明每个推荐 Skill 由哪个员工在什么 Task 中使用。
6. Task 运行时只加载实际需要的 Skill，不把全部 Skill 注入所有员工。
7. 生成结果中的断裂关系、孤立字段、缺失能力和权限问题在创建前被发现并解释。
8. 新增一种公司模板只需新增模板包，不需要修改核心数据库枚举、通用页面或 Task 引擎行业分支。
9. 小说模板完整运行在通用引擎上，现有数据和流程无破坏性迁移。
10. 模板更新不会静默覆盖公司的本地修改。

## 17. 设计决策摘要

- 采用声明式模板包，不采用行业专用页面堆叠。
- 使用公司模板架构师 Skill 生成草案，不生成新 Skill。
- AI 输出结构化数据，HTML 由平台安全渲染。
- 默认先生成、后确认、再创建；确认页鼓励先采用推荐方案，创建后随时调整。
- 字段能力表现为维护协议；员工在 Task 中按需使用现有 Skill。
- 平台提供通用知识与成果中心，模板决定行业术语和视图。
- 健康问题必须可解释、可定位并给出安全修复入口。
