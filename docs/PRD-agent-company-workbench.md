## Problem Statement

当前 Muster 以 Leader 拆分任务、临时 Worker 执行、Verifier 验证为核心。Worker 没有长期身份、项目上下文、稳定职责、独立任务队列和持续协作关系，完成子任务后即结束。这种模式适合一次性任务，但无法支持以下工作：

- 多个有固定职责的 Agent 长期参与同一个项目。
- Agent 按组织、通信和工作流关系自主协作，而不是全部依赖主管派发。
- Agent 在信息不足时与派发者补充沟通，完成后唤醒上游工作。
- 项目持续运行、暂停、恢复、定时触发和阶段复盘。
- 文件、任务、引用、成果和责任关系长期可追踪。
- 用户通过公司与项目看板理解运行状态并及时纠偏。
- 同一套内核支持小说、文档、PPT、网页等不同类型的 Agent 公司。

用户需要的不是“主管加若干一次性子 Agent”，而是一套本地 Agent 公司操作系统：用户可以创建公司、部门、员工、协作关系和项目；Agent 以持久身份在项目内持续工作，并通过 Task 系统完成异步协作。

## Solution

Muster 将提供一个本地单用户 Agent 公司工作台。

用户通过模板和 AI 引导快速创建公司。公司拥有部门、员工、组织关系、通信权限和工作流。所有实际工作归属于项目；每个员工进入项目后拥有项目隔离的上下文和运行线程，可以同时参与多个项目且互不串线。

系统使用 Task 作为统一运行单元。员工可以自动派发符合通信协议的内部 Task、补充上下文、等待依赖、恢复执行和反馈成果。定时触发、事件触发、临时讨论、纠正工作和阶段复盘均建立在同一个 Task 系统上。

用户通过类似群聊的公司与项目窗口和第一负责人沟通，并通过组织图、流程图、员工状态、Task 状态、成果预览和轮次复盘看板观察工作。系统持续运行，只有用户主动暂停、强制复盘，或剩余工作全部被必须由用户决定的问题阻塞时才整体等待。

第一版以长篇小说创作公司验证完整闭环，同时保持公司模板、执行器、Skill、成果处理器和项目类型可扩展。

## Product Principles

1. **项目优先**：公司定义组织与能力，项目承载目标、上下文、Task、成果和汇报。
2. **身份与执行器分离**：员工不是模型或进程；Claude Code、模型 API 和外部服务只是可替换能力。
3. **确定性平台，显式智能责任**：系统负责队列、状态、锁、权限、传输和校验；需要语义判断的工作必须由明确的 Agent 完成。
4. **持续运行但可控**：没有阻塞或暂停原因时继续工作；有明确的检查点、成本统计和死循环保护。
5. **默认简单，高级可配**：模板和 AI 生成可运行默认值，复杂配置按需展开。
6. **职责边界优先**：每类正式成果有责任岗位，其他岗位通过 Task 请求，不越权直接修改。
7. **无静默覆盖**：任何并发写入都不得导致文件丢失或无提示覆盖。
8. **可追踪**：Task、消息、成果、引用、执行线程和用户纠正形成完整来源链。
9. **视图不冒充事实**：人物关系图等派生视图只展示权威资料，不允许直接修改造成内容错乱。
10. **本地先行，云端可迁移**：首版不承担多租户、支付和云部署，但核心模型不得绑定本地 Claude Code。
11. **复杂能力，简单入口**：首次使用遵循“公司类型 → 组建团队 → 新建项目 → 发布 Task”；日常启动直接恢复上次项目和待处理事项，高级能力按需展开。
12. **员工身份高于执行器**：员工绑定固定 CLI 或 API 执行器；员工之间通过 Task 协作，执行器不是组织角色，也不能替代员工身份。
13. **执行器配置可共享，运行实例必须隔离**：同一 CLI/API 可被多个员工使用，但 session、项目线程、进程、Task worktree、日志和中止信号不得共享。
14. **记忆分层且可重建**：员工身份、个人记忆、公司任职记忆、项目记忆、会话历史和 Task 沙盒分层保存；任何 CLI/API session 都只是缓存，员工上下文必须能由 Muster 重建。
15. **模板是完整公司能力包**：模板包含向导、部门、员工职责、能力包、通信关系、工作流、成果协议、权限默认值、执行器要求和健康检查，不只是工作流图。
16. **共享能力，不共享隐私**：员工能力包和公司模板可分享；个人记忆、公司/项目数据、会话、凭据和本地路径只保留在本地。

## vNext Primary User Journey

### 首次启动

1. 选择一个本地总工作区。
2. 选择公司类型或模板。
3. 使用模板推荐岗位组建团队，可从本地员工库招募或新建员工。
4. 配置公司默认执行器，按需为个别员工固定覆盖。
5. 在总工作区内创建一个独立项目目录。
6. 发布第一个自然语言 Task 并进入项目工作台。

### 日常启动

- 默认回到上一次打开的项目，不重复展示建司向导。
- 优先显示需要用户处理、正在工作和最近完成的 Task。
- 用户可以随时切换项目、增加公司、招募员工或修改工作流。
- 原始模型日志、CLI 参数、线程、镜像和 Token 细节默认收进高级区域。

## Domain Model

### Workspace

Workspace 是本地 Muster 的总工作区，保存公司和项目目录的默认根路径。一个 Workspace 可以包含多个公司；一个公司可以包含多个项目；每个项目使用独立目录和 Git 仓库。Agent Home、运行时、记忆索引和 Muster 管理的执行器安装位于 Workspace 的私有 `.muster/` 区域，不写入用户项目仓库。

### Company

公司保存通用组织、员工、部门、通信关系、工作流、Skill 分配、执行器配置和公司运行契约。

公司具有以下运行状态：

- 下班：允许修改组织和员工配置，不执行新 Task。
- 上班：组织配置锁定，项目线程可以领取并执行 Task。
- 排空：停止领取新 Task，当前 Task 完成或安全保存后进入暂停。
- 强制复盘：等待用户查看轮次汇总并点击继续。

上班期间允许为当前项目增加或减少员工镜像，因为镜像只增加同职责并行执行能力，不改变组织语义。

### Company Contract

每家公司必须拥有简短的公司章程，作为所有员工始终加载的公共规则。复杂配置保存在结构化数据中，按需加载，不把整份组织和流程定义塞入每次模型上下文。

公司运行契约定义：

- 公司目标和基本原则。
- 部门、员工与职责。
- 组织关系、通信权限和工作流。
- 成果类型、责任岗位与完成标准。
- Skill、工具与项目文件权限。
- 冲突、阻塞、复盘和外部操作规则。

### Department

部门是可寻址、可展示、可配置的组织实体，可以没有主管。首版内部 Task 默认派发到个人，不要求实现部门自动路由。部门可维护共享规则、员工集合和看板。

### Agent Profile

Agent Profile 是用户本地员工库中的全局持久身份，包含：

- 名称、稳定人格、工作原则和通用能力。
- Skills、工具需求和可负责的成果类型。
- 个人长期记忆和用户偏好。
- 推荐执行器能力和默认权限模板。

Agent Profile 可以被公司引用、仅能力复制或完整快照复制。对外分享只能导出无记忆、无凭据、无会话和无本地路径的能力包。

### Company Employee

Company Employee 是 Agent Profile 在一家公司的任职实例，包含：

- 部门、岗位和职责。
- 可负责的成果类型。
- 可联系对象和协作协议。
- Skills、工具权限和项目文件权限。
- 固定执行器配置引用；可以继承公司默认执行器或显式覆盖。
- 定时 Task 和事件订阅。
- 只属于当前公司的任职记忆。

任职配置只允许在公司下班状态修改。配置修改后再次上班即使用新配置。多个公司引用同一个 Agent Profile 时共享基础身份、能力和用户允许共享的个人通用记忆，但公司任职记忆、项目记忆、权限、Task 和执行器 session 相互隔离。

### Project

所有实际工作必须属于项目。一个项目可以是一整本小说、一个章节、一个网站或一个 PPT，由用户自行决定边界。

每个项目独立保存：

- 项目说明和初始 Task。
- 项目文件、成果和结构化资料。
- Task 序列、讨论、引用和事件。
- 员工项目线程与镜像。
- 定时器、事件触发器和轮次复盘。
- Token、成本和运行统计。

新项目的 Task 从自身序列开始，不继承其他项目的 Task。项目可以只读挂载其他项目或其中的成果作为参考源；修改必须回到来源项目。

### Project Agent Thread

员工在每个项目中拥有独立运行线程和项目上下文。不同项目中的同一员工可以并行工作，不存在现实员工的单一容量冲突。

模型会话、缓存和压缩属于执行层实现细节。系统应优先复用有上下文价值的热会话并使用提供商缓存，但员工身份和项目记忆不能只存在于模型会话。会话丢失或轮换后，Muster 必须能从 Agent Profile、公司任职记忆、项目记忆、线程摘要和当前 Task 重建上下文。

### Mirror

镜像是当前项目内某个员工的临时并行执行线程：

- 只在当前项目生效。
- 与根员工职责、权限、项目上下文和 Task 池相同。
- 自动领取根员工队列中的待处理 Task。
- 已被一个镜像领取的 Task 不能被其他镜像重复领取。
- 成果和复盘统一归入根员工，不单独列为正式员工。
- 监察员只能建议增加镜像，不能自行扩容。
- 项目结束时释放；减少镜像时先完成或安全保存当前 Task。

### First Responsible Agent

公司必须配置第一负责人；每个项目可以指定自己的第一负责人，默认继承公司设置。

第一负责人负责：

- 接收用户消息。
- 拆解当前阶段工作并派发 Task。
- 跟踪阻塞、冲突和依赖。
- 将用户纠正意见转成修正 Task。
- 汇总项目轮次进展并向用户反馈。

第一负责人与主业务执行岗位必须分离。长篇小说模板中，项目第一负责人不能同时担任主写手。

### Operations Inspector

运营监察是不可删除的系统基础角色，可修改模型和检查策略，但不负责业务内容。它检查：

- 员工与镜像运行状态。
- Task 队列长度、紧急程度、截止时间和拥堵。
- 长时间无进展、重复调用、循环重试和异常退出。
- 关键员工下班导致的流程断裂。
- 积分、Token 和成本异常。
- 临时工与子任务的健康聚合：在岗数量、失败率、预算消耗以及是否在产出有效成果。
- 失败分类的准确性，以及被系统静默吞掉、只留在日志里的失败必须被显式上报和可见。
- 是否建议用户增加项目镜像或调整项目流程。

监察员只能提醒、催促、暂停异常 Task 和提出建议，不能自行修改组织、增加镜像或改变项目方向。

## Task System

### Task Is the Runtime Unit

“邮箱”“工作清单”“反馈池”和“定时工作”统一由 Task 系统表达，不建立相互独立的概念。

每个 Task 至少记录：

- 项目内序号和内部全局 ID。
- 根 Task、父 Task、依赖和延伸关系。
- 派发者、原始接收人和实际执行镜像。
- 优先级、紧急程度、创建时间和截止时间。
- 输入协议、上下文引用、输出协议和完成条件。
- 状态、检查点、结果、成果引用和反馈。
- Token、缓存、工具调用、时间和估算费用。

### Task States

核心状态包括：

- 排队。
- 已领取。
- 执行中。
- 等待派发者补充。
- 等待其他 Task。
- 安全暂停。
- 阻塞。
- 已完成。
- 失败。
- 已取消。

领取必须使用原子租约和心跳。执行线程异常时，租约可以过期并由系统恢复 Task，但不得造成重复提交。

### Task Dispatch Protocol

通信关系定义结构化输入与输出协议。派发者必须整理工作包，包含：

- 任务目标。
- 前情和派发原因。
- 当前需要解决的问题。
- 必要文件、段落和上游成果引用。
- 已知限制与禁止改变的事实。
- 期望输出和完成标准。

系统只负责提供表单、机械预填当前 Task 已引用的资料和校验必填字段，不负责判断语义相关性。

接收者发现信息不足时，将原 Task 标记为等待补充，在同一个 Task 讨论中向派发者追问。派发者完成当前工作后优先处理补充请求。达到配置的最大补充轮次仍无法继续时，上报第一负责人。

### Task Ordering

- 当前 Task 默认不被普通反馈打断。
- 员工完成当前 Task 后领取队列顶部的可执行 Task。
- 同优先级内容按原始入队顺序处理，而不是按结果返回顺序倒排。
- 队首 Task 尚未满足依赖时，可以跳过并处理下一项可执行 Task。
- 用户纠正和明确紧急 Task 可以进入队首，但仍在当前 Task 完成或安全暂停后执行。

### Task Chains

任务的深化、补充、纠正和后续行动通过任务链表达。新项目不会继承来源项目的 Task；跨项目只保留成果引用。

Task 完成后的反馈默认解除上游 Task 的等待状态，而不是为每条反馈创建新的“查看结果”任务。主动汇报或上游 Task 已结束时，才创建新的建议或查看 Task。

## Triggers and Discussions

Task 支持以下触发来源：

- 用户或第一负责人派发。
- 员工在执行范围内自主派发。
- 事件触发，例如章节完成。
- 定时触发，例如每日连续性检查。
- 用户纠正。
- 运营监察告警。

员工之间的临时讨论也是一种特殊 Task，必须具有：

- 目标和触发原因。
- 允许参与的空闲员工。
- 最大轮次、时长、Token 和积分预算。
- 父 Task 或独立建议归属。
- 结构化结论或“无有效结论”。

正式 Task 的优先级高于闲置讨论。参与者收到正式工作后，在当前发言结束后退出讨论；剩余成员可以继续，人数不足时提前结束。讨论结论只能形成给用户查看的建议，由第一负责人汇总，不能自动修改成果或创建正式执行工作。

## Continuous Operation and Review Cycles

项目在以下条件下持续工作：

- 用户未主动暂停。
- 未到强制复盘点。
- 仍存在可执行 Task。
- 并非所有剩余工作都被必须由用户决定的问题阻塞。

普通进度汇报不暂停工作，可以按小时、每天或完成数量触发。

用户可以设置强制复盘频率。达到阈值后：

1. 停止领取新 Task。
2. 当前 Task 完成或安全保存。
3. 第一负责人生成轮次复盘看板。
4. 用户查看、按摘要序号填写备注。
5. 第一负责人将备注转换为检查或修正 Task。
6. 用户必须点击“继续工作”才能恢复。

复盘看板按根员工聚合若干结果，不逐条罗列 Task。每条摘要仍保留到相关 Task、成果和执行线程的隐藏追踪关系。

### Organizational Memory and Self-Evolution（组织记忆与自我进化）

公司的目标不只是完成单次工作，而是让每一次执行都使下一次更接近"一次做对、减少返工"。这要求公司具备跨越单次任务的记忆与自我进化能力。设计详见 `docs/superpowers/specs/2026-08-12-organizational-memory-system-design.md`。

记忆按稳定度分三层：工作记忆（当前任务上下文，任务结束即归档）、经验记忆（任务反思沉淀的教训与规则，按事件累积）、结构记忆（组织形态本身：员工能力、工作流、工具配置与用户偏好画像）。三层之间由四条流串联：感知执行数据 → 反思为经验 → 晋升为结构改动 → 装配回下次执行上下文。其中"晋升流"是从单次经验上升为组织级结构进化的桥梁，是公司真正学会一件事的关键。

事后反思是公司的"做梦"机制：任务级反思整合当日执行，周期性反思把碎片化的经验巩固为结构性改进，每日组织级汇总产出可执行的优化建议。这些反思在条件允许时自主进行，但绝不妨碍正式工作，也不直接修改组织——产出仍走建议、审批与可回滚的落地通道。

自我进化默认自动进行，但必须满足三条约束：所有结构变更有完整版本历史可还原；可被自动优化的要素允许用户手动锁定（个人锁与组织锁），锁定后该要素不再被自动优化；改工作流、权限、增裁员工等高风险变更仍需用户确认，低风险改进（如用户偏好、惯用工具、提示词原则）可自动落地。用户始终保留对进化方向与节奏的最终控制。

进化的对象是通用的：用户偏好画像、惯用工具与工具质量、工作流交接模式、员工能力与提示词，适用于任何公司模板而非特定场景。公司不应把同样的偏好重复问用户、把同样的工具反复试错、把同样的交接路径反复手动配置——这些都应该在一次执行后被记住，并在下一次自动生效。

默认不要求用户设置项目总预算，因为新用户难以预估。系统必须按公司、项目、员工、Task、模型和执行器统计：

- 输入与输出 Token。
- 缓存创建和命中。
- 工具调用和运行时间。
- 估算费用或积分。

镜像数据默认聚合到根员工，可展开查看。

用户可以按公司或项目设置预算上限。普通上限采用软限制：达到后停止领取新 Task，当前 Task 完成后暂停。

死循环保护独立于预算，至少包括：

- 最大单次运行时间。
- 最大模型轮次和工具调用。
- 重复失败和重复计划检测。
- 长时间无文件、状态或输出进展。
- 心跳丢失。

确认无进展或达到绝对安全限制时，必须保存检查点并终止当前 Task，由监察员向第一负责人报告。

失败必须分级诊断，而不是一律按同一策略处理：系统应区分瞬时可重试、能力缺口、配置错误和永久失败，并据此决定重试、补能力、转人工或放弃。跨公司外包等带退避的重试不得无限进行——达到退避上限必须转为永久失败并上报，避免持续做无用功。临时工与子任务的健康看板与死循环保护同等重要，是一等观测面。

## Execution and Capability Model

员工身份与执行器完全分离。执行器可以是：

- 本地 Codex CLI、Claude Code CLI、Gemini CLI 或其他受支持 CLI。
- 文本模型 API。
- 视觉模型 API。
- 音频、图像、视频或其他外部服务。
- 后续插件提供的运行环境。

用户可以调整员工的模型、执行器、Skills 和工具，但必须在公司下班状态修改。执行器能力不足或连续失败时，系统暂停相关 Task，展示可用选择和成本，由用户决定是否切换；系统不得擅自调用未授权或更昂贵的服务。

API 凭据统一保存于用户级安全凭据库。员工、项目、公司模板和导出文件只能引用连接 ID，不得读取或保存原始密钥。

所有 CLI 和 API 文件工具默认只能写入当前 Task worktree，并只读访问当前项目和用户明确挂载的参考目录。访问其他本地目录必须由用户授权。权限由“审批策略 × 允许范围”统一表达；Turbo 只是“无需审批”与项目、工作区、指定目录或整机范围的组合。

能力的来源包括内置执行器、本地与社区 Skill、MCP 服务和外部 CLI/API 服务。系统对这些能力的推荐应基于真实使用质量（成功率、耗时、是否被反复弃用），而不是仅凭“已安装”或“已声明”。“平台是 carrier 不是 provider”与“推荐安装”之间存在张力：经审核的精品能力可以一键安装启用，未经审核的能力只作建议、仍由用户确认；这一边界由权限与审批统一承载，不在执行模型中另开例外。

### System Settings（基础程序设置）

系统设置分四类，作为程序的通用基础能力（设计见 `docs/superpowers/specs/2026-08-12-settings-overhaul-design.md`）：

- **网络**：HTTP 代理（留空=直连且不读取系统环境变量）、代理例外（逐主机直连）、自定义 CA 证书（注入模型/MCP/命令工具与渲染层）、出口超时。网络配置修改后需重启生效。
- **外观**：主题（深/浅/跟随系统）、界面字体、主文本字号、界面语言（中/英）、代码块主题。
- **生成参数**：思考深度按模型归一化（关/低/中/高，不支持的模型自动隐藏），上下文缓存按 provider 启用。
- **并发**：按执行器设定最大并发并可锁定（如套餐仅允许 1 并发）；未锁定时系统根据失败情况自适应下调、健康后试探上调，均不超过硬上限。

## Skills and Templates

系统需要以下内建引导 Skill：

- 创建公司。
- 创建项目。
- 创建员工。
- 创建部门。
- 生成或修改工作流。
- 公司与项目体检。
- 创建项目镜像。

Skill 分为系统、岗位、项目和工具类型。公司模板只声明所需 Skill，不包含凭据。

用户和系统可以从能力商城发现并引入 Skill 与配套能力（MCP、工具档案；设计见 `docs/superpowers/specs/2026-08-14-capability-marketplace-design.md`）。商城既提供人工策展、可一键安装启用的精品条目，也允许手动添加第三方来源；所有条目都带能力标签、安装方式、依赖与质量信号。能力被使用后的结果（成功、失败、耗时）会回流为质量反馈，用于修正推荐排序，使“推荐”反映真实可用性而非仅凭注册时的声明。

### 需求驱动的项目启动与能力发现

项目创建或新的项目任务开始时，必须先记录用户认可的预期效果、受众、风格/表现手法、约束、交付物、资料需求及参考资料。系统据此展示固定执行器、能力绑定、任务级可加载 Skill 和启用工具的发现快照；工具档案库只是候选实现目录，既不代表已安装/已授权，也不强制员工使用。

需要视觉效果确认的任务，用户必须确认视觉参考或设计稿后才能进入制作。未完成「需求 → 能力发现 → 资料/视觉确认（如需要）→ 用户确认」的项目任务不得创建生产工作单，服务端也必须执行该边界。

纯提示词 Skill 可以快速确认启用。包含脚本、命令、文件写入或外部连接的 Skill 必须展示权限清单并由用户批准。

「需求 → 能力发现 → 缺口 → 补齐 → 确认 → 执行」不只在项目立项时发生一次，也是每个生产任务执行前的预检环节。任务被领取后、进入执行前，系统应基于任务目标判断所需能力是否齐备：齐备则照常执行；发现缺口时，优先从已有的优质外部资源（商城、MCP、社区 Skill、既有方法）中调研并引入现成方案，而不是从零自造工具——「先借再造，除非迫不得已」是产品原则。缺口补齐需要安装或授权外部能力时，仍遵守上一段的权限确认边界。

### Company Creation

第一版以“行业模板 + 对话修改”为主要入口，空白搭建放入高级模式。

创建公司 Skill：

1. 获取用户目标和公司类型。
2. 选择基础模板和类型扩展包。
3. 生成简短公司章程、员工、部门、组织图、通信图和工作流。
4. 展示可视化预览和自动体检结果。
5. 用户确认团队并配置公司默认执行器。
6. 创建首个项目并发布第一个 Task 后上班。

新增员工时，用户只需描述职责。Skill 自动建议 Skills、工具、成果责任、可联系对象、输入输出协议和执行器，用户确认默认配置即可。

当前公司创建采用严格的声明式蓝图，而不是让模型直接生成页面或脚本：

1. 系统级 `company-template-architect` Skill 根据用户目标和基础行业包生成结构化草案。
2. 草案统一包含部门、员工、上下级与通信关系、员工交接流程、业务记录字段、视图、自动化、Task 输入输出协议和能力绑定。
3. 服务端先执行 Zod Schema 与确定性引用校验；生成失败时回退到可编辑的内置模板，并向用户展示稳定提示。
4. 客户端只用受信任的 React 组件渲染六个模块，不执行草案里的 HTML、JavaScript、命令或新 Skill。
5. 用户必须先确认蓝图，再配置执行器并创建；确认后的精确快照、模板版本和员工/字段能力绑定会随公司保存。

模板中的业务 Skill 必须绑定到具体岗位、员工或字段，并说明用途与加载时机。Task 执行时按 `requiredSkillIds`、`requiredCapabilityIds` 和 `knowledgeTargets` 解析；只有命中的 Skill 进入上下文，缺失或停用项形成可解释诊断。模板架构 Skill 不负责生成或审核新的 Skill，也不会自动安装外部 Skill。

公司设置提供模板运行健康面板。字段负责人缺失、能力绑定指向失效员工、绑定 Skill 不可用、计划任务目标失效等问题会以稳定指纹持久化、去重，并展示发生原因、影响、建议及对应配置入口。用户可暂时忽略提醒；问题消失后记录转为已解决。

## Workbench UX

### Main Surfaces

- 公司列表与公司创建入口。
- 公司对话窗口。
- 项目对话窗口。
- 公司、部门、员工和项目看板。
- 可拖拽组织图、通信关系图和工作流图。
- Task 详情与受限讨论。
- 成果工作台。
- 轮次复盘页面。
- Token、成本和健康状态页面。

### Conversation

公司和项目窗口采用类似群聊的交互。用户可以：

- 与第一负责人对话。
- `@` 允许联系的员工或部门。
- 临时邀请员工进入受 Task 约束的讨论。
- 查看关键事件摘要。
- 展开查看完整 Task 对话。

主窗口不铺开所有内部消息，只展示领取、派发、等待、阻塞、完成、成果和告警等关键事件。

### Graph Editing

组织图、通信图和工作流图是第一版核心功能：

- 支持拖动节点和连线。
- 支持侧边栏下拉和属性编辑。
- 支持自然语言修改后预览差异。（v1 已实现：见实施清单 2026-07-06 推进记录）
- 公司上班时只读，下班时可编辑。
- 保存前自动校验关键岗位缺失、断裂流程、非法通信和无责任人的成果类型。

### Artifact Workbench

成果工作台使用可扩展的成果处理器。第一版支持：

- Markdown 和纯文本查看、编辑。
- 小说章节、大纲和设定卡片。
- 人物关系、组织和流程图。
- 图片与 PDF 只读预览。
- 其他文件的基本信息和调用系统默认应用打开。（v1 已实现：见实施清单 2026-07-06 推进记录）

复杂的 PPT、Word、网页和视频内置编辑器不进入第一版。

成果分为：

- 权威可编辑成果，例如正文、计划大纲和正式设定。
- 管理成果，由指定责任岗位维护。
- 派生只读视图，例如实际人物关系、已发生时间线和伏笔状态。

用户不会直接编辑人物关系投影视图。需要调整时，与项目第一负责人对话；负责人派发相互关联的修正 Task，更新正文和正式资料后重新生成派生视图。

## Safe Artifact and File Handling

Task 状态、领取锁、消息、任务链和运行统计以数据库为唯一运行账本。Markdown 等文件只保存业务成果。

成果注册表记录：

- 成果 ID、类型和位置。
- 当前责任岗位。
- 创建及修改它的 Task。
- 来源、引用和关联成果。
- 并发、锁定和发布策略。

系统必须提供“共享读取视图 + Task 隔离写层”：

- Agent 读取相同项目资料和最新正式成果。
- 修改先写入系统内部隔离层。
- 提交时检查基础内容是否已经变化。
- 文本非重叠修改可以三方合并。
- 同一区域冲突不得静默覆盖。
- PPT、图片、数据库等无法可靠合并的资源使用独占锁。
- 每次正式写入前保存可回滚快照。

并发策略由成果类型决定，而不是所有 Task 使用同一种方案。

## Long-form Novel Company

### Project Initialization

项目必须由用户指定初始 Task，不能仅凭项目说明自动开工。用户可以：

- 创建全新任务。
- 在同一项目中延伸已有 Task。
- 基于当前成果继续深化。
- 创建新项目并只读引用其他项目成果。

初始化采用“对话生成结构化设定，用户可视化修改”：

- 题材和子类型。
- 目标受众和内容边界。
- 故事梗概、核心冲突和预计篇幅。
- 视角、时态和叙事距离。
- 文风、节奏、对白和描写偏好。
- 参考样文和禁用表达。
- 世界观、人物、大纲和章节结构。

项目说明保持简短，由 AI 自动生成，用户确认项目目标、交付物、引用来源、完成条件和复盘频率后再确认开工。

### Base Roles

首个模板至少包含：

- 项目第一负责人。
- 主写手。
- 人物设计。
- 情节架构。
- 运营监察。

可选类型扩展包增加：

- 世界观。
- 时间线。
- 伏笔。
- 连续性检查。
- 功法或力量体系。
- 历史、科学或专业研究。
- 文风编辑与审校。

第一负责人与主写手必须分离。每类正式成果指定唯一责任岗位；岗位镜像可以执行同一职责，其他岗位只能通过 Task 请求修改。

### Rolling Workflow

小说项目只做滚动规划：

1. 建立全书级方向和阶段大纲。
2. 详细规划当前若干章节或一个复盘轮次。
3. 派发创作和专业维护 Task。
4. 完成章节时提交章节变更摘要。
5. 事件触发人物、时间线、伏笔和情节进度维护 Task。
6. 定时 Task 检查遗漏和长期一致性。
7. 到复盘点后等待用户确认并进入下一阶段。

### Novel Views

第一版小说可视化至少包括：

- 可拖拽计划大纲。
- 实际剧情进度。
- 人物关系图。
- 项目进度和轮次复盘。

计划大纲可以编辑；实际剧情、人物关系、已发生时间线和伏笔状态是只读投影视图。

## User Stories

1. 作为用户，我希望选择长篇小说公司模板并用几句话描述需求，以便快速创建可工作的 Agent 公司。
2. 作为用户，我希望 AI 自动生成员工、部门、关系和流程，以便不用从空白画布开始。
3. 作为用户，我希望在确认前看到组织和流程图，以便发现明显不合理之处。
4. 作为用户，我希望拖动节点和连线修改组织与流程，以便直观定制公司。
5. 作为用户，我希望用自然语言修改公司关系，以便不理解图编辑器时也能配置。
6. 作为用户，我希望公司上班后锁定组织配置，以便运行期间不发生结构漂移。
7. 作为用户，我希望一键上班和下班，以便控制公司是否领取新工作。
8. 作为用户，我希望员工下班时保存当前工作，以便再次上班后继续。
9. 作为用户，我希望为公司指定第一负责人，以便有统一的沟通对象。
10. 作为用户，我希望每个项目可以指定自己的第一负责人，以便多个项目独立协调。
11. 作为用户，我希望第一负责人与主写手分离，以便主写手专注正文。
12. 作为用户，我希望通过简单流程新增员工，以便快速补充新的专业职责。
13. 作为用户，我希望员工配置默认由 AI 推荐，以便只确认少量关键设置。
14. 作为用户，我希望员工只能联系被允许的对象，以便协作关系保持可控。
15. 作为用户，我希望员工之间使用结构化请求协议，以便接收者获得足够信息。
16. 作为派发 Agent，我希望整理前情、原因、引用和输出要求，以便接收者直接工作。
17. 作为接收 Agent，我希望信息不足时在原 Task 中追问，以便补齐资料后继续。
18. 作为用户，我希望追问轮次有上限，以便 Agent 不会无限互问。
19. 作为用户，我希望所有实际工作归属于项目，以便上下文和成果不会混杂。
20. 作为用户，我希望同一员工可以同时参与多个项目，以便复用公司能力。
21. 作为用户，我希望同一员工在不同项目中使用独立上下文，以便资料不会串线。
22. 作为用户，我希望新项目拥有独立 Task 序列，以便项目历史清晰。
23. 作为用户，我希望只读挂载其他项目成果，以便参考资料而不误改来源。
24. 作为用户，我希望指定项目初始 Task 后才开工，以便明确工作起点。
25. 作为用户，我希望 Agent 根据进度滚动规划，以便避免产生大量过期 Task。
26. 作为用户，我希望员工可以在职责范围内自动派发内部 Task，以便项目持续运行。
27. 作为用户，我希望 Task 包含状态、优先级、依赖和成果引用，以便理解工作进展。
28. 作为用户，我希望反馈唤醒原来等待的 Task，以便不产生大量重复查看任务。
29. 作为用户，我希望 Task 按原始派发顺序处理，以便结果返回顺序不扰乱计划。
30. 作为用户，我希望等待依赖的 Task 不阻塞其他可执行工作，以便公司继续运行。
31. 作为用户，我希望为项目中的员工创建镜像，以便临时增加并行处理能力。
32. 作为用户，我希望镜像自动领取根员工的积压 Task，以便真正缓解拥堵。
33. 作为用户，我希望镜像不会重复领取同一 Task，以便避免重复工作和反馈。
34. 作为用户，我希望镜像成果归入根员工，以便看板不会变得碎片化。
35. 作为用户，我希望监察员建议镜像扩容但不自动执行，以便控制成本。
36. 作为用户，我希望定时 Task 可以独立唤醒员工，以便执行周期性检查。
37. 作为用户，我希望章节完成后触发维护 Task，以便项目资料及时更新。
38. 作为用户，我希望定时检查作为事件更新的兜底，以便发现遗漏和长期冲突。
39. 作为用户，我希望空闲员工可以参与有边界的头脑风暴，以便发现新想法。
40. 作为用户，我希望头脑风暴有轮次和成本限制，以便不会无休止闲聊。
41. 作为用户，我希望头脑风暴只生成建议，以便不会擅自改变项目。
42. 作为用户，我希望看到普通进度汇报而不中断工作，以便随时了解状态。
43. 作为用户，我希望设置强制复盘间隔，以便控制错误累积。
44. 作为用户，我希望复盘按员工成果汇总而不是罗列 Task，以便快速阅读。
45. 作为用户，我希望用摘要序号给第一负责人备注，以便快速提出纠正意见。
46. 作为用户，我希望强制复盘后手动点击继续，以便明确批准下一轮工作。
47. 作为用户，我希望看板显示员工状态、Task 数量、拥堵和流程断裂，以便发现问题。
48. 作为用户，我希望监察员检测卡死和重复行为，以便避免无声停滞。
49. 作为用户，我希望系统统计每个项目、员工和 Task 的 Token，以便了解消耗。
50. 作为用户，我希望默认不必估算总预算，以便降低创建项目的难度。
51. 作为用户，我希望后续可设置成本上限，以便控制长期运行费用。
52. 作为用户，我希望达到软限制后完成当前 Task 再暂停，以便不损坏工作。
53. 作为用户，我希望死循环达到绝对上限时强制保存并终止，以便系统可恢复。
54. 作为用户，我希望为员工选择 Claude Code 或模型 API，以便按任务能力组合执行器。
55. 作为用户，我希望能力不足时由我决定是否切换模型，以便控制成本和授权。
56. 作为用户，我希望凭据不出现在员工和项目文件中，以便避免密钥泄露。
57. 作为用户，我希望 Skill 的权限在启用前可见，以便避免执行危险脚本。
58. 作为用户，我希望 Claude Code 默认只能访问当前项目，以便保护本地其他文件。
59. 作为用户，我希望所有项目文件变更都不会静默覆盖，以便避免成果丢失。
60. 作为用户，我希望文本非冲突修改可以自动合并，以便保持并行效率。
61. 作为用户，我希望二进制成果使用独占锁，以便避免文件损坏。
62. 作为用户，我希望冲突只阻塞相关成果，以便其他 Task 继续工作。
63. 作为用户，我希望每次正式写入前有快照，以便发生问题时回滚。
64. 作为小说用户，我希望通过对话初始化题材、文风和故事设定，以便减少表单填写。
65. 作为小说用户，我希望提供参考样文生成风格档案，以便文风更贴近预期。
66. 作为小说用户，我希望查看和编辑计划大纲，以便控制剧情方向。
67. 作为小说用户，我希望查看人物关系图，以便理解人物网络。
68. 作为小说用户，我希望人物关系图保持只读，以便不会与正文事实脱节。
69. 作为小说用户，我希望直接编辑章节正文，以便参与创作。
70. 作为小说用户，我希望正文变化触发相关资料同步，以便项目资料保持一致。
71. 作为用户，我希望预览图片和 PDF，以便在工作台查看常见成果。
72. 作为用户，我希望其他复杂成果可以调用外部应用打开，以便首版不受格式限制。
73. 作为用户，我希望 Task 和成果之间可以互相追踪，以便理解每项结果从何而来。
74. 作为用户，我希望旧测试数据无需迁移，以便新架构可以从干净状态开始。

## Implementation Decisions

### Replace the Legacy Orchestration Core

- 不保留旧“快速任务”产品模式。
- 旧 Leader→Worker→Verifier 编排不作为新系统兼容层。
- 复用成熟的进程启动、流式输出、调度、沙盒、备份和基础 WebSocket 能力。
- 新建公司运行时、项目运行时、Task 引擎和成果系统。
- 旧 `.muster` 测试数据不迁移，可在重构阶段清理。

### Deep Modules

以下模块应封装为可独立测试的深模块：

1. **Company Definition Engine**：公司契约、部门、员工、三类关系图和上班锁定。
2. **Project Runtime**：项目生命周期、员工项目线程、镜像和运行状态。
3. **Task Engine**：状态机、原子领取、依赖、追问、反馈、恢复和任务链。
4. **Trigger Engine**：事件触发、定时触发和受限讨论。
5. **Communication Protocol Engine**：关系权限、输入输出协议和补充轮次。
6. **Execution Adapter Layer**：Claude Code 与后续 API/外部服务适配。
7. **Context and Session Manager**：项目隔离、热会话复用、压缩和上下文引用。
8. **Artifact Registry**：成果元数据、责任岗位、引用、派生视图和处理器注册。
9. **Safe Workspace Engine**：隔离写层、资源锁、合并、快照和回滚。
10. **Inspector**：心跳、无进展、拥堵、流程健康和成本检测。
11. **Reporting Engine**：非阻塞汇报、强制复盘、员工级聚合和来源追踪。
12. **Template and Skill Engine**：公司创建、员工创建、项目初始化和权限确认。

### Persistence

- 本地单用户首版使用事务型数据库保存控制状态。
- 文件系统保存项目业务成果和导出内容。
- Task 状态不得以 Markdown 文件作为唯一运行源。
- 任务事件和成果来源应追加记录，支持恢复和审计。
- 配置文件与数据库之间必须有单一权威来源，避免双写漂移。

### Frontend

- 当前单文件前端不适合继续承载图编辑、项目工作台和复杂状态。
- 新前端应按公司、项目、Task、成果、图编辑和看板拆分模块。
- 组织图、通信图和工作流图使用统一节点/边模型，但语义和校验规则分离。
- 小说人物关系图复用图渲染基础设施，但保持只读投影视图。
- 实时状态继续通过 WebSocket 或等价事件通道推送。

### API Contracts

- API 围绕公司、项目、员工、关系、Task、触发器、成果、报告和用量资源设计。
- 所有状态变更必须返回最新状态和可追踪事件 ID。
- 领取、完成、暂停、恢复和发布成果必须具备幂等键。
- 文件发布和 Task 完成不得由两个互不一致的请求分别提交。

### Configuration Editing

- 公司上班状态禁止修改正式员工、部门、职责和关系。
- 项目镜像是唯一允许在上班期间执行的组织容量变更。
- 用户直接修改项目权威内容时，生成变更事件并通知第一负责人。
- 使用旧内容的相关 Task 在安全点暂停；无关 Task 继续。

## Testing Decisions

### Test Philosophy

- 测试外部可观察行为和状态转换，不锁定内部实现细节。
- 状态机、调度、领取锁、权限和文件安全必须使用确定性测试。
- LLM 语义质量不以固定字符串断言；使用结构协议、模拟执行器和可控结果验证。
- 任何“不会重复执行”“不会丢文件”“不会跨项目泄漏”的声明必须有回归测试。

### Required Test Areas

1. 公司上下班与配置锁定。
2. 项目隔离和跨项目只读挂载。
3. 同一员工多项目并行。
4. 项目镜像领取、租约、心跳和回收。
5. Task 状态机、依赖、追问、反馈和恢复。
6. 事件触发与定时触发去重。
7. 临时讨论轮次、退出和预算限制。
8. 强制复盘的排空、暂停和继续。
9. 监察员无进展、死循环和拥堵判断。
10. Token 与成本归集。
11. 通信权限和协议必填校验。
12. 凭据不可见和文件访问边界。
13. 文本自动合并、冲突阻止、二进制锁和回滚。
14. 成果责任岗位和派生视图只读限制。
15. 公司模板、员工创建和项目初始化生成结果校验。
16. 长篇小说从初始 Task 到章节完成、资料更新和轮次复盘的端到端闭环。

### Test Infrastructure

- 为 Task、公司和项目状态机建立纯内存测试适配器。
- 为执行器建立可编排的假模型，模拟成功、追问、超时、无进展和工具失败。
- 为时间和定时器提供虚拟时钟。
- 为文件层提供临时目录和并发提交测试。
- 为 UI 建立关键用户路径的浏览器测试。
- 当前仓库没有正式测试套件，第一阶段必须先建立最小测试命令和 CI 可运行入口。

## Success Metrics

首个长篇小说 MVP 达标必须满足：

1. 用户可以在十分钟内从模板创建并启动公司。
2. 用户无需手写配置文件即可创建项目和初始 Task。
3. 至少五个固定岗位可以持续完成一轮小说协作。
4. 一个员工可以在不同项目中并行且上下文不串线。
5. 同一项目可创建镜像并保证 Task 不重复领取。
6. 信息不足可以在 Task 内补充并自动恢复。
7. 章节完成可以触发资料维护 Task。
8. 达到复盘点后项目正确排空并等待用户继续。
9. 用户能看到按员工汇总的进度、阻塞和成本。
10. 并行文件修改不存在静默覆盖和成果丢失。
11. 强制终止后 Task 可以从检查点恢复或明确失败。
12. 用户可以查看和编辑正文、查看计划大纲和人物关系图。

## Out of Scope

第一版不包括：

- 网站注册、多租户、团队账号和云同步。
- 积分购买、支付、订阅和商业计费。
- 云端托管 Agent 环境。
- 自动切换模型或未经授权调用外部 API。
- 完整 PPT、Word、网页 IDE、音视频编辑器。
- 部门智能路由和部门任务自动认领。
- 监察员自动创建镜像或修改公司结构。
- 头脑风暴建议自动执行。
- 每个 Task 自动创建 Verifier。
- 旧 Muster Task 数据迁移。
- 跨公司共享项目资料。

## Further Notes

- “公司、员工、上班”等是面向用户的产品隐喻。工程模型必须使用明确状态和资源，不应把现实员工的单线程容量、邮箱或考勤逻辑错误套入 Agent。
- 员工在不同项目中天然拥有并行线程；只有同一项目中同一员工的 Task 积压才需要镜像。
- 第一版目标不是证明“Agent 越多越好”，而是证明持久职责、结构化协作、项目隔离和持续运行能产生比单 Agent 更稳定、可控的长篇小说成果。
- 产品设计完成后，应再形成详细数据模型、状态机和 API 设计文档；这些工程文档不得改变本 PRD 的用户语义。
