# 复盘 0002：迁移外键规程缺失，空库测试掩盖真实库风险

**日期**：2026-08-18 company 物理去列终审发现并修复　**级别**：高危（真实库损坏风险）　**状态**：已修复

## 事实

- 公司概念退役批次 D 需要 22 张表去列/改名/删除（迁移 A–E），SQLite 改列必须走"建新表→搬数据→DROP 旧表→改名"的表重建法。
- 按 SQLite 官方规程，表重建期间必须 `PRAGMA foreign_keys=OFF`，否则 DROP 被未重建子表的外键拒绝，或触发级联误删。
- 修复前：迁移 runner 在逐文件事务里以 FK=ON 执行——真实库上迁移要么报错中断，要么级联删掉本不该删的行；而**测试环境是空库**，没有任何 FK 依赖可违反，全部测试绿灯通过。

## 根因

迁移 runner 没有实现 SQLite 官方表重建规程（FK=OFF + 文件内 `foreign_key_check`）；更深一层：**验证环境与目标环境结构性不一致**——空库没有历史数据、没有 FK 图，"迁移在空库跑通"与"迁移在真实库安全"是两个命题。

## 为什么自检没拦住

- 集成测试全部基于 `makeTestDb()` 从零建库，FK 违规在空库上不可能发生；agent 自检（全量测试过）对这类问题天然失明。
- 迁移代码 review 容易只看 SQL 列清单是否对账，不看你**怎么执行** SQL。

## 补强了什么

- `runMigrations`：逐文件事务**外** `PRAGMA foreign_keys=OFF`，文件执行后跑 `foreign_key_check`，有违规即整体回滚该文件。
- 真实库迁移强制先备份到 `~/.muster-backups/`（脚本 `scripts/company-drop-migrate-real-db.mts` 留档：备份→清垃圾→迁移→断言全过）。
- 断言清单显式化：foreign_key_check 为空、目标表单行、漏网列已删。

**教训**：迁移类改动的验证必须在"有历史数据 + 完整 FK 图"的库上做；空库测试给的绿灯是假信心。执行环境（PRAGMA/事务边界）与 SQL 内容同等重要。
